## القسم C — Content Platform
### النظام 17 — Post Creation & Publishing
**System ID:** CNT-017  
**Priority:** Critical  
**Phase:** MVP  
**Specification status:** Working specification; reconcile against the user's canonical Document 01 and full Section C source before final sign-off.

> This file records the one exact system title available from the prior project context: **Post Creation & Publishing**. The remaining Section C system titles (18–27) are intentionally not invented here.

## 1. الوظيفة والهدف
تمكين المستخدم المسجل من إنشاء منشور ونشره بصورة موثوقة، مع دعم النص والوسائط التي يسمح بها إصدار MVP، والتحقق من الملكية والخصوصية والقيود على الخادم قبل اعتبار المنشور منشورًا. يجب ألا تعرض الواجهة نجاحًا قبل تأكيد حفظ البيانات.

## 2. رحلة المستخدم
1. يفتح المستخدم محرر إنشاء المنشور.
2. يكتب النص ويضيف صفرًا أو أكثر من الوسائط المسموح بها حسب حدود MVP.
3. يعرض التطبيق معاينة محلية، وحالة الرفع/الحفظ، وأي أخطاء تحقق مفهومة.
4. يرسل التطبيق طلب الإنشاء مع بيانات الوسائط المسموح بها فقط.
5. يتحقق الخادم من الجلسة، وحالة الحساب، وحدود الحجم والعدد والنوع، وملكية ملفات الوسائط.
6. ينشئ الخادم المنشور ويربط الوسائط به ضمن عملية قابلة للتعافي من الفشل.
7. لا تظهر حالة Published إلا بعد تأكيد العملية؛ عند الفشل يحتفظ التطبيق بالمسودة المحلية إن أمكن ويعرض سببًا آمنًا وإمكانية إعادة المحاولة.

## 3. الشاشات والحالات
- Composer: حقل النص، اختيار الوسائط، معاينة، زر نشر.
- Media preparation: انتظار، ضغط محلي إن أمكن، فشل قراءة/تحضير الملف.
- Upload/publish: تقدم واضح دون ادعاء اكتمال مبكر.
- Validation: نص فارغ، ملف غير مدعوم، تجاوز الحد، حساب مقيد.
- Success: المنشور المؤكد ومعرّفه.
- Failure/offline: لا فقدان صامت للنص، ولا تكرار للنشر عند إعادة المحاولة.
- Accessibility/RTL: ترتيب صحيح للوحة المفاتيح، وصف للوسائط، حالات التركيز، ورسائل عربية واضحة.

## 4. العمليات والقواعد
- إنشاء المنشور عملية موثقة للمستخدم الحالي؛ لا يقبل الخادم `author_id` موثوقًا من العميل.
- التحقق من حالة الحساب ومنع النشر للحسابات المحظورة أو المقيّدة وفق نطاق العقوبة.
- رفض النص الفارغ بعد إزالة المسافات، مع السماح بنشر وسائط فقط إذا كانت سياسة المنتج تسمح بذلك صراحة.
- حدود MVP المرجعية الحالية للوسائط: 10 ملفات كحد أقصى، 50 MiB لكل ملف، و100 MiB إجماليًا للمنشور؛ يجب أن يفرض الخادم الحدود نفسها أو حدودًا أشد، ولا يكفي تحقق Flutter.
- أنواع الوسائط المسموح بها تُحدد بقائمة سماح؛ لا يُعتمد على امتداد الملف أو MIME المرسل من العميل وحده.
- تحقق من توقيع الملف ومحتواه في جهة موثوقة قبل إتاحته للعامة؛ فحص العميل قابل للتجاوز.
- لا يُنشأ سجل منشور عام يشير إلى ملف لم يكتمل رفعه والتحقق منه.
- إعادة المحاولة تستخدم idempotency key أو آلية مكافئة لمنع إنشاء منشورات مكررة.
- ترتيب النشر والوقت ومؤشرات الحالة يحددها الخادم.
- التعديل والحذف يخضعان لملكية المنشور وسياسة الاحتفاظ والتدقيق.
- أي mention أو hashtag أو location يمر عبر تحقق مستقل وسياسة خصوصية؛ لا تُستنتج صلاحيات من نص المنشور.

## 5. التحكم والخصوصية
- الكاتب يملك المنشور ويمكنه تعديل/حذف ما تسمح به السياسة.
- رؤية المنشور تخضع لحالة الحساب وخصوصية الملف وعلاقات الحظر والجمهور المختار.
- لا يُكشف مسار Storage داخلي أو bucket خاص أو بيانات EXIF/موقع غير مقصود.
- الروابط الخاصة بالوسائط تُصدر وفق سياسة وصول مناسبة، مع مراعاة أن الروابط الموقعة قد تبقى صالحة حتى انتهاء مدتها.
- لا يحق للعميل تغيير حالة المراجعة أو عدد المشاهدات أو بيانات التدقيق.
- RLS يجب أن يمنع إنشاء منشور باسم مستخدم آخر أو ربط مرفق لا يملكه المستخدم.

## 6. الاعتماديات
- Supabase Auth للجلسة والهوية.
- PostgreSQL وRLS لبيانات المنشور والملكية.
- Supabase Storage لمسارات الوسائط وسياسات القراءة/الكتابة.
- Flutter composer وحالات الرفع/الخطأ.
- سياسات Document 07 للأمان والخصوصية والإشراف.
- حدود Document 08 للتكلفة والحصص.
- عقود Document 06 لإنشاء المنشور ورفع الوسائط.
- لا يعتمد MVP على خدمة مدفوعة لمعالجة الفيديو أو CDN خارجي أو AI.

## 7. الاستثناءات والتعافي
- انقطاع الشبكة قبل الإرسال: الاحتفاظ بالمسودة محليًا.
- انقطاع أثناء الرفع: تنظيف الملفات/السجلات الجزئية بأمان، أو السماح باستكمال رفع موثوق إن كان مدعومًا.
- نجاح رفع الوسائط وفشل إدراج المنشور: حذف الكائنات اليتيمة بعد مهلة آمنة أو إدخالها في cleanup queue.
- نجاح الإدراج وفشل استجابة العميل: إعادة المحاولة بنفس idempotency key وإرجاع المنشور الموجود بدل تكراره.
- تجاوز الحصة: رفض واضح دون حذف مسودة المستخدم.
- ملف تالف أو نوع مضلل: رفضه وعدم إتاحته للقراءة العامة.
- حساب مقيّد: إظهار حالة المنع وسبب عام آمن، دون كشف قواعد مكافحة الإساءة الداخلية.

## 8. الأمان والإساءة
- فرض rate limits وحصص نشر ورفع على الخادم.
- فحص صلاحية الجلسة والملكية عند كل mutation.
- عدم قبول Storage paths عشوائية أو روابط ملفات خارجية كأنها مرفقات موثوقة.
- مقاومة replay والطلبات المكررة.
- حماية من HTML/script injection والروابط الخبيثة عند العرض؛ لا تعرض النص كـHTML موثوق.
- الإبلاغ والحظر يظلان فعالين بعد النشر، ويجب أن ينعكس الإخفاء/التقييد على كل طرق القراءة.
- الاحتفاظ بسجل أمني محدود دون تخزين نصوص حساسة في logs.

## 9. نقاط التفوق
- تجربة كتابة ونشر سريعة وواضحة، مع حفظ مسودة محلية وحالات رفع صادقة.
- دعم عربي RTL من البداية مع عدم كسر النص المختلط.
- معالجة محلية للصور لتقليل استهلاك البيانات والتكلفة.
- تصميم offline-aware دون ادعاء النشر عند عدم الاتصال.
- حماية الخصوصية والملكية من جهة الخادم، لا من الواجهة فقط.

## 10. المرحلة ومعيار القبول
**Phase:** MVP / Critical.

لا يُعد CNT-017 مكتملًا حتى تنجح الاختبارات التالية:
- إنشاء منشور نصي بحساب صالح.
- رفض مستخدم غير مسجل أو حساب مقيّد حسب السياسة.
- رفض إنشاء منشور باسم مستخدم آخر عبر API مباشرة.
- رفض ملفات غير مسموحة أو تتجاوز حدود العدد/الحجم على الخادم.
- منع ربط ملف Storage يخص مستخدمًا آخر.
- عدم ظهور منشور قبل اكتمال التحقق من مرفقاته.
- إعادة المحاولة بعد timeout لا تنشئ منشورًا مكررًا.
- تنظيف أو تسجيل الملفات اليتيمة بعد فشل العملية.
- احترام الخصوصية والحظر في استعلامات القراءة والروابط الموقعة.
- الاحتفاظ بالمسودة عند فشل الشبكة دون عرض نجاح كاذب.
- نجاح اختبارات RTL وإمكانية الوصول والحالات الفارغة/التحميل/الفشل.
- وجود اختبار تكاملي بحسابين مستقلين، وليس اختبار واجهة فقط.
