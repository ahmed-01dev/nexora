## Verified database security
- Profile SELECT visibility now checks for a block before allowing any non-owner access path (public, accepted follow, friendship, or shared conversation). The profile owner can still read their own profile.
- The private-profile friendship path now requires `friendships.status = 'accepted'`; pending, declined, and cancelled requests do not grant profile visibility.
- Direct client updates to `profiles.is_private` are revoked; the RPC updates it together with `user_private_settings.profile_visibility` to avoid divergent privacy state.
- Direct authenticated INSERT/UPDATE privileges on `user_private_settings` are revoked. The authenticated `update_privacy_settings` RPC remains executable and is the single write path for these settings.
- Private avatar/cover Storage reads now use the same visibility paths as the profile row, including accepted friendship and allowed shared conversation, while retaining block checks.
- Private-account privacy now overrides a story's per-story public setting for both the story row and the underlying signed Storage path; only the owner or accepted followers can view stories from a private account.
- Friends-only post media signed URLs now allow accepted friends under the same conditions as the post-row RLS policy; the previous helper omitted that visibility branch.
- Device registration uses an upsert on `(user_id, push_token)`. The authenticated role now has the necessary owner-scoped column UPDATE grants for `user_id`, `platform`, and `push_token`; the `user_devices_update_own` policy still limits writes to the current user.
- The Storage media path helper denies non-owner access to media attached to soft-deleted posts, matching the post-row RLS behavior.
- The home feed now calls a SECURITY INVOKER server-side paging RPC that joins accepted follows and accepted friendships, while preserving underlying RLS; this avoids sending unbounded relationship ID lists from the client.
- Direct-conversation membership now becomes false for both participants when either side blocks the other. Because the existing RLS policies use this helper, the block prevents further direct-message access, message reads, attachment reads, and conversation previews while leaving group/community conversations unaffected.
- Pending friend requests and pending follow requests cannot be accepted after a mutual block. Follow and friendship relationship rows are hidden from both participants while the block exists; relationship rows are retained so unblocking can restore them.
- A direct-message creator cannot remove the other participant from a 1:1 conversation; creators can still manage members in group/community conversations. Appeal INSERT privileges are restricted to author, action, and message fields; status/reviewer/resolution metadata is staff-controlled.
- All inspected public application tables have RLS enabled.
- Previous grant checks found no anonymous table privileges on the current public application tables.
- Community-channel authenticated grants are limited to SELECT/INSERT/DELETE.
- Notification UPDATE is limited to `read_at`; authenticated clients cannot alter recipient, actor, type, payload, or entity metadata.
- Message-attachment SELECT filtering requires a non-deleted message and conversation membership. Image attachment MIME/size/message-type checks are RESTRICTIVE and therefore combine with uploader/path/object ownership checks.
- Profile usernames have a unique index on `lower(username)`, preventing case-only duplicates.
- A follow-up catalog audit found one missed PUBLIC EXECUTE grant on `private.request_friend_impl(uuid)`. It was revoked. Verified afterward: anon cannot execute the helper, authenticated can execute it, and authenticated can still execute the public invoker RPC wrapper `public.request_friend(uuid)`.
- A fresh catalog check found no remaining SECURITY DEFINER functions in the `private` schema with PUBLIC EXECUTE.
- No public or private SQL views were returned by the view inventory query.
